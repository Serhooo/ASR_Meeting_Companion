# Техническое задание (PRD): «Meeting Companion» — локальный ИИ-ассистент встреч для Windows (портативный)

> Версия 2 (исправленная). Правки к исходному ТЗ внесены после проверки реального API
> библиотек и целевой машины — см. «Приложение Б: История правок».

## 1. Общее описание продукта

Meeting Companion — полностью автономное десктопное приложение для ОС Windows.
Оно работает локально, обеспечивая конфиденциальность пользовательских данных.
Приложение автоматически записывает аудио (микрофон + системный звук), распознаёт
речь на русском языке и генерирует краткий протокол встречи (Summary) с выводами,
договорённостями и задачами.

## 2. Технологический стек и ИИ-архитектура

* **Язык разработки:** Python 3.10+ (проверено: на целевой машине Python 3.13 — совместим).
* **Интерфейс (GUI):** CustomTkinter (тёмная тема, макет в духе GigaPlatform AI Studio).
* **Захват аудио:** sounddevice + numpy (WASAPI loopback для одновременного захвата
  микрофона и звука собеседников; проверено: sounddevice 0.5.6 уже установлен).
* **Обработка аудио:** scipy.io.wavfile / numpy. Системный FFmpeg приложению
  **не требуется** — записи сохраняются в 16 kHz моно WAV и читаются scipy;
  ffmpeg остаётся требованием только самого пакета gigaam при работе
  с произвольными форматами (`gigaam/preprocess.py::load_audio`).
* **Распознавание речи (ASR):** локальная модель семейства **GigaAM-v3**
  (github.com/salute-developers/GigaAM), инференс на PyTorch (torch).
* **Суммаризация (LLM):** локальный сервер **Ollama**, модель на выбор
  пользователя (llama3.2 / qwen2.5 / mistral и др. — см. 4.1).
  **Портативность:** официальный бандл Ollama хранится в `tools/` проекта,
  распаковывается в `ollama/`, модели — в `ollama_models/` (`OLLAMA_MODELS`
  указывает внутрь проекта); сервер запускается приложением как дочерний
  процесс на 127.0.0.1:11434 и останавливается вместе с ним. Системная
  установка Ollama не требуется (но подхватывается, если уже есть).

### 2.1 Режимы выполнения: CPU / GPU (обязательный выбор устройства)

Требование: поддерживать **два варианта запуска** — выбор устройства
закреплён за пользователем и доступен в настройках GUI:

| Режим | Описание | Когда использовать |
|---|---|---|
| **Авто** (по умолчанию) | `cuda`, если `torch.cuda.is_available() == True`, иначе `cpu` | На любых машинах «без головной боли» |
| **CPU** | Принудительный инференс только на процессоре, без GPU | Ноутбуки без NVIDIA GPU (в т.ч. целевая машина: Intel Iris Xe) |
| **CUDA** | Принудительный инференс на GPU NVIDIA | Машины с видеокартой NVIDIA; явный контроль за VRAM |

Реализация (соответствует реальному API GigaAM):

```python
import torch, gigaam

def resolve_device(mode: str) -> str:
    if mode == "CPU":
        return "cpu"
    if mode == "CUDA":
        if not torch.cuda.is_available():
            raise RuntimeError("Выбран CUDA, но GPU NVIDIA не обнаружен")
        return "cuda"
    return "cuda" if torch.cuda.is_available() else "cpu"   # AUTO

model = gigaam.load_model(
    "v3_e2e_ctc",          # версия модели (см. 2.2)
    fp16_encoder=True,     # применяется библиотекой ТОЛЬКО на cuda; на cpu безопасно игнорируется
    use_flash=False,
    device=resolve_device(user_mode),   # None -> авто; либо "cpu" / "cuda" явно
)
```

Правила:

* В GUI (настройки) — выпадающий список «Устройство ASR: Авто / CPU / CUDA».
  Выбор сохраняется между запусками (локальный config.json).
* Режим «CUDA» без установленного torch с CUDA-поддержкой или без GPU →
  вежливая ошибка в статусной строке с предложением переключиться на CPU.
* fp16-энкодер и `torch.autocast` задействуются только на GPU; на CPU инференс
  всегда fp32.
* VRAM-чанкинг (п. 4.2) активен в режимах CUDA/AUTO-with-GPU; на CPU вместо переполнения
  VRAM контролируется потребление RAM (чанки всё равно применяются).

### 2.2 Версии моделей GigaAM (уточнение)

Доступные версии ASR-моделей семейства v3 (короткие имена эквивалентны полным):

| Имя | Особенности |
|---|---|
| `ctc` / `v3_ctc` | Базовый CTC |
| `rnnt` / `v3_rnnt` | RNN-T декодер |
| `e2e_ctc` / `v3_e2e_ctc` | **Рекомендуется по умолчанию**: end-to-end, с пунктуацией и нормализацией текста |
| `e2e_rnnt` / `v3_e2e_rnnt` | E2E + RNN-T (тяжелее) |

Веса скачиваются автоматически в `~/.cache/gigaam` при первом запуске
(проверка md5-контрольной суммы). **Первый запуск требует интернет; далее — полная автономность.**
Версия модели выбирается пользователем в настройках, по умолчанию `v3_e2e_ctc`.

## 3. Функциональные требования и архитектура модулей

### Модуль 1: Двойной захват аудио (Audio Capture Engine)

* Входные потоки:
    1. Системный микрофон (ввод пользователя).
    2. Системный динамик/наушники (выход конференции — Zoom, Teams, браузер).
* Реализация под Windows: sounddevice с хост-API WASAPI в режиме **loopback**
  (захват исходящего звука без виртуальных аудиокабелей).
* Смешивание: на лету объединять два потока в один моно-сигнал
  с частотой дискретизации **16000 Гц** (стандарт GigaAM; `SAMPLE_RATE = 16000`).
* Сохранение: по окончании записи — аудио в локальный кэш `meeting_cache.wav`.

### Модуль 2: Локальное распознавание (ASR Engine)

* Загрузка модели: `gigaam.load_model(..., device=resolve_device(mode))` —
  см. п. 2.1 (CUDA при наличии и выборе, иначе CPU; фолбэк гарантирован).
* Обработка: `meeting_cache.wav` передаётся в пайплайн распознавания.
* **Длинные записи:** API GigaAM само разбивает материал при превышении
  `LONGFORM_THRESHOLD = 25 сек` и возвращает `LongformTranscriptionResult`
  со списком сегментов `Segment(text, start, end)` (опционально пословные таймкоды
  `word_timestamps=True`). Это закрывает требование устойчивости: длинная встреча
  не переполняет память, сегменты обрабатываются батчами.
* **Таймкоды:** формат `[MM:SS] Текст реплики` строится из `segment.start`
  (без внешнего VAD и самодельного чанкинга — используем встроенный механизм модели).
* Рекомендация для CPU-режима: CTC-модели (`v3_e2e_ctc`) декодируют быстрее RNNT.

### Модуль 3: Интеллектуальный суммаризатор (LLM Core)

* Интеграция: REST-запрос к локальному Ollama (http://localhost:11434,
  endpoint `/api/chat`, `stream=false`).
* Модель: настраиваемая пользователем (см. 4.1). На CPU-машине рекомендованы
  компактные модели (`llama3.2:3b`, `qwen2.5:3b`); `llama3:8b` / `mistral:7b`
  допустимы, но медленны на ноутбучном CPU.
* Системный промпт (промпт-инжиниринг):
  «Ты — профессиональный секретарь. Проанализируй этот транскрипт встречи и составь
  краткий протокол на русском языке строго по трем блокам: 1. Принятые решения.
  2. Ключевые договорённости. 3. Следующие шаги (Задачи с дедлайнами/исполнителями,
  если упомянуты). Выведи ответ в формате разметки Markdown.»
* Экспорт: сохранение итогового текста в файл `.md`.

### Модуль 4: Графический интерфейс пользователя (GUI)

* Стиль: тёмная тема, неоновые/зелёные акценты, скруглённые углы, шрифты Roboto/Segoe UI.
* Основные элементы экрана:
    * Левая панель: кнопка «Записать встречу», **кнопка «⏸ Пауза»**
      (запись на паузе — звук не пишется, таймер замирает; при снятии с паузы
      фиксируется перерыв и в будущий транскрипт вставляется тайм-код
      `[MM:SS] ⏸ Перерыв (пауза N с)` — только в режиме «Встреча»),
      статус-индикатор времени (таймер 00:00:00), переключатель режима
      «Встреча»/«Реалтайм»,
      **кнопка «Обработать запись»** (ручной запуск пайплайна ASR → LLM —
      автозапуска по остановке нет, момент обработки выбирает пользователь;
      кнопка доступна, если есть сохранённая запись, и позволяет
      переобработать её после смены настроек), визуализатор аудиоволны,
      прогресс распознавания, статус.
    * Центральная панель («Протокол встречи»): вкладки **«Тема»**
      (редактируемая повестка/участники — передаётся LLM как контекст при
      составлении протокола, кэшируется в `cache/meeting_topic.txt`,
      попадает в шапку экспорта), «Решения», «Договорённости»,
      «Следующие шаги», «MD».
    * Панель транскрипта: боковое скроллируемое текстовое поле с таймкодами.
    * Нижний блок: кнопка «Экспорт протокола в MD» и статусная строка
      «Ваши данные никогда не покидают компьютер».
* **Настройки (новый обязательный элемент):** выбор устройства ASR
  (Авто / CPU / CUDA), версия модели GigaAM, модель Ollama, папка экспорта.

### Модуль 4b: Режимы записи — «Встреча» / «Реалтайм» (добавлено)

Переключатель под таймером (состояние сохраняется):

* **Встреча** (по умолчанию) — полный цикл: запись → чанкинг → транскрипт →
  протокол (как в исходном ТЗ).
* **Реалтайм** — параллельно с записью ведётся живая транскрибация:
  скользящий 16 kHz буфер, энергетическая сегментация (порог RMS + пауза
  0.7 с, макс. реплика 8 с), каждый сегмент распознаётся тензорным путём
  GigaAM; текст появляется в панели транскрипта с задержкой **~2–4 с**.
  Требование по быстроте подтверждено замером на целевой машине
  (i5-11320H: инференс ~в 5–10 раз быстрее реального времени).
  По остановке запускается штатный пайплайн — точный транскрипт заменяет
  черновой живой текст, затем строится протокол.

## 4. Нефункциональные требования

### 4.1 Автономность

Все веса моделей и логика выполнения изолированы на локальной машине.
Допускаются внешние сетевые запросы **только при первичной настройке**
(однократная загрузка весов GigaAM и `ollama pull` модели); после этого —
полная автономия. В рантайме приложение сетевых обращений не выполняет.

### 4.2 Производительность (уточнено по целевой машине)

| Сценарий | Ожидание |
|---|---|
| Часовая встреча, GPU уровня RTX 3060/4060 | 3–5 минут (режим CUDA) |
| Часовая встреча, CPU-only (целевая машина: i5-11320H, 4C/8T, без dGPU) | Ориентировочно 15–40 минут — реальная оценка уточняется замером при разработке; GUI обязан показывать прогресс распознавания (%, ETA) |
| Суммаризация Ollama на CPU | Компактные модели (3B) — единицы минут; 7–8B — заметно дольше |

### 4.3 Устойчивость

Автоматическое разбиение длинных аудиозаписей на сегменты (встроенный
long-form механизм GigaAM, порог 25 с) — для контроля VRAM/RAM.
Все тяжёлые операции (запись, ASR, LLM) выполняются в фоновых потоках;
GUI не блокируется. Ошибки (нет ffmpeg, нет Ollama, нет CUDA при выборе CUDA)
сообщаются в статусной строке, приложение не падает.

### 4.4 Зависимости окружения (проверено на целевой машине)

| Компонент | Статус | Действие |
|---|---|---|
| Python 3.13 | ✅ установлен | — |
| sounddevice 0.5.6, numpy | ✅ установлены | — |
| FFmpeg | ⭕️ не требуется приложению | Наш пайплайн использует тензорный путь GigaAM (16 kHz WAV читается scipy) — ffmpeg нужен только при прямом использовании пакета gigaam |
| Ollama | ❌ не установлена | Установка + `ollama pull llama3.2:3b` (или др.) |
| PyTorch, CustomTkinter, gigaam | ❌ не установлены | `pip install -r requirements.txt` (CPU-сборка torch по умолчанию; CUDA-сборка — по желанию) |
| GPU NVIDIA | ❌ отсутствует (Intel Iris Xe) | Работа в режиме CPU/Авто; режим CUDA — для машин с NVIDIA |

## Приложение Б: История правок (верификация исходного ТЗ)

1. **«Принудительное ускорение CUDA»** → заменено на обязательный трёхрежимный выбор
   устройства Авто / CPU / CUDA (новый п. 2.1). Причина: на целевой машине нет
   NVIDIA GPU (Intel Iris Xe) — режим CPU обязан работать штатно.
2. **Точное API GigaAM:** указан реальный вызов `gigaam.load_model(name, fp16_encoder=…, device=…)`
   и реальные имена версий (`v3_e2e_ctc` и др.); «GigaAM-v3» как абстракция → конкретные версии.
3. **Таймкоды:** подтверждено, что модель возвращает `Segment(text, start, end)`
   (long-form, порог 25 с) — требуемый формат `[MM:SS]` строится из `segment.start`,
   внешний VAD/чанкинг не требуется. Убрано противоречие «структурированный транскрипт
   с таймкодами» без источника таймкодов.
4. **FFmpeg:** добавлен как обязательная зависимость окружения — GigaAM грузит аудио
   через subprocess-вызов ffmpeg (проверено в исходниках). На целевой машине не установлен.
5. **«Полное отсутствие внешних сетевых запросов»** → уточнено: только после первичной
   загрузки весов (CDN GigaAM + ollama pull); в рантайме сети нет.
6. **Производительность:** добавлена честная оценка CPU-режима (п. 4.2) и требование
   прогресса/ETA в GUI; на i5-11320H час встречи — «десятки минут», не 3–5 минут.
7. **LLM на CPU:** llama3 8B на ноутбучном CPU будет крайне медленным → рекомендованы
   компактные модели (llama3.2:3b, qwen2.5:3b), выбор модели — в настройках.
8. **Настройки GUI** добавлены как обязательный элемент интерфейса (устройство, версия
   GigaAM, модель Ollama).
